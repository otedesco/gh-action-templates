# OPS-176 Node LTS and Package-Manager Contract Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Establish one accepted, machine-verifiable Node.js and package-manager contract across the shared setup action, all seven product repositories, CI workflows, and Docker builds.

**Architecture:** Record the runtime decision in an ADR owned by `gh-action-templates`, then encode the same exact versions in a small version contract and a contract test. Consumer manifests, lockfiles, workflows, and Dockerfiles adopt that contract without opportunistic dependency upgrades. The check fails closed on missing, ranged, or divergent versions.

**Tech Stack:** Node.js, Corepack, pnpm, npm for the Next.js application only if explicitly retained by the ADR, GitHub Actions, Docker, Node test runner.

---

## Scope and sequencing

- Linear issue: `OPS-176` (urgent, estimate M, due 2026-09-06).
- Central repository: `gh-action-templates`.
- Consumers: `cerberus`, `hermes`, `notify`, `server-utils`, `commons`, `cache`, and `web-app`.
- This task precedes `OPS-177` and `OPS-178`; those plans must consume this decision rather than selecting versions independently.
- Keep dependency versions unchanged except for package-manager metadata generated by the selected tool.
- Treat exact versions as data. Do not duplicate a range such as `>=8.6.10` or a moving label such as `lts/*`.

**Step 2: Add the focused test command**


Do not add a test dependency when the built-in Node test runner is sufficient.

**Step 3: Run the test and capture the baseline failure**

Run:

```bash

```

Expected: FAIL and report the current `18.17.0`/`18.17.1`, `8.6.10`/`8.15.6`, missing Node engines, ranged pnpm engines, and npm-only `web-app` differences.

**Step 4: Write and accept the ADR**

In `ADR-001-node-package-manager-contract.md`, record:

- status and decision date;
- exact Node LTS patch version and support window;
- exact pnpm version for packages/services;
- whether `web-app` remains npm or migrates to pnpm;
- Corepack policy and lockfile ownership;
- local, CI, and Docker enforcement points;
- upgrade procedure, including one coordinated PR and lockfile regeneration;
- compatibility evidence for SWC, Next.js, Jest, Vitest, and production images.

The chosen values must be explicitly approved before continuing. Put those exact values in `runtime-contract.json`; do not infer them from the current drift.

**Step 5: Commit the red contract and accepted decision**


## Completion checklist

- The ADR is accepted and names exact supported versions.
- All manifests, lockfiles, setup actions, workflows, and Dockerfiles agree.
- Clean frozen installs and Docker builds pass.
- Contract tests reject missing, ranged, moving, or divergent versions.
- No dependency upgrade or package-manager exception is undocumented.
- Evidence is linked back to `OPS-176`.
